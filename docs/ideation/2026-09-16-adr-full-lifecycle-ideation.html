Ideation · Compound Engineering

ADR Full Lifecycle

Date 2026-09-16 Topic adr-full-lifecycle Mode repo-grounded Raw → survivors 45 → 29 merged → 7

Focus: break out ADR support across the whole decision lifecycle — loading the current state of decisions, shaping the drivers behind them, drafting a specific decision, reviewing and refining the document, validating that teams follow it in practice, and eventual supersession or retirement — plus a reviewer set checking well-formedness, technology-adoption governance, product strategy, the -ilities, testability, evidence of spikes and prototypes, and multi-stakeholder legibility.

Grounding Context

What exists today

  • 10 skills (skills/<name>/SKILL.md, all status: draft), 7 commands, 3 agents (adr-historian, architecture-reviewer, fitness-author), 5 hooks, 4 ADRs in docs/adr/, 3 node:test files.
  • Drafting is the strong stage. commands/decide.md runs a 7-step flow; the ADR skill teaches a six-question anatomy, a five-dimension options table, and an eight-item quality checklist.
  • Progressive disclosure exists in exactly one place and was verified: skills/architectural-trade-offs/decision-archetypes/ is 5 files totalling 781 lines behind a 131-line parent, with a routing table and “Load only the archetype file you need.”
  • The reviewer runs exactly four lettered checks A–D, all scoped to the git diff, with severity flags 🟥 / 🟧 / 🟨 and an explicit contract: “You do not gate merges. You surface findings; the user decides.”

Where the lifecycle stops

  • Context-loading is filename-deep. hooks/session-start.sh counts ADRs with find | wc -l and picks “Latest” by sorting filenames. It never opens an ADR body — no statuses, no supersession chains, no Proposed backlog.
  • Drivers have no home. A search across the 63 tracked files finds no strategy, product, drivers, requirements, principles, constraints or roadmap file. The characteristics skill says the prioritization “IS an architectural decision” needing its own ADR — and no such ADR exists.
  • Document review is absent as a step. The quality checklist is prose nothing executes; /review checks the diff against ADRs, never the ADR text.
  • The taught format is in none of the real ADRs. A grep for option|alternativ|considered|rejected|dimension across all four docs/adr/*.md returns zero matches — verified twice.
  • Evidence vocabulary is absent entirely. A repo-wide grep for spike|prototype|proof of concept|PoC|benchmark returns one hit, and it is an unrelated homonym (“should handle spikes” → scalability).
  • Revisit triggers are write-only. Every substantive ADR has them; nothing reads them. The one trigger that ever fired was noticed by a human and narrated in prose inside a successor document.
  • fitness/adr-format is named as the canonical worked example in three files and no fitness/ directory exists. No test references docs/adr/ at all.
  • A live routing bug. commands/decide.md sends the historian to ~/.claude/CLAUDE.md; agents/adr-historian.md, commands/review.md, the README and docs/architecture.md all make repo-local ./ARCHITECTURE.md primary. This repo has no root ARCHITECTURE.md.

Hard constraints every idea had to clear

  • Cross-product only. A skill that encodes one product's internals, data model or stack is out of scope, so strategy and -ilities lenses must be taught generically.
  • Admission bars. A new skill needs an activation phrase distinct from every existing skill; a new command needs more than three steps; a new agent needs context isolation, heavy parallel work, or worktree writes; a new hook needs strong signal-to-noise plus an SA_PLUGIN_HOOKS opt-out name.
  • ADR-0003 owns a rename contract toward consumers, and ADR-0004 prices a breaking rename at a major version bump plus a second PR in the marketplace repo and a designated release actor. Keeping the architecture-decision-records name stable and decomposing beneath it avoids all of that.

Three claims verification knocked down

  • ADRs carry no frontmatter at all. They are plain adr-tools output, and test/lib/frontmatter.mjs is explicitly not a YAML parser — flat scalars, block scalars and comma-lists only, applied to skills, commands and agents, never to docs/adr/. Any idea resting on nested ADR frontmatter is new machinery, not a field addition.
  • ADR-0002's “beyond ~15 skills” trigger has not fired. The plugin is at 10. Proximity is a reason for discipline, not urgency.
  • There is no scheduler. None of the five workflows carries a schedule: or cron: trigger; all CI is push- or PR-triggered. Any “periodic sweep” has to ride an existing PR-triggered check.

Topic Axes

  1. Decision-state awarenessHow the plugin loads, represents and surfaces what has already been decided.
  2. Decision driversThe repo-wide factors — prioritized -ilities, strategy, governance rings, constraints — that shape decisions before any single one is drafted.
  3. Drafting and evidenceShaping a specific decision: options development, archetypes, spikes and prototypes.
  4. Review lensesThe reviewer set, and how lenses are structured, dispatched and reported.
  5. Conformance and decision agingValidating teams follow the decision in practice, plus revisit triggers, supersession and retirement.

Ranked Ideas

  1. Review lenses as a loadable catalog, split by decidability
  2. Ship fitness/adr-format — with the routing-table drift as its first assertion

  5. Drivers as a numbered ADR — a utility tree the lenses can check against

  7. Decision aging without a scheduler
1

Review lenses as a loadable catalog, split by decidability

Review lenses Confidence 85% Complexity Medium
Description

Build the reviewer set as review-lenses/*.md — one file per lens behind a routing table inside the existing ADR skill — mirroring the decision-archetypes/ shape exactly: trigger conditions, a rubric, a ## Hand-Off. Then split the set by what kind of thing each lens is. Well-formedness, radar and governance cross-reference, testability, and evidence-presence are decidable from structure, so they run as fitness checks in CI and can fail a build. Product-strategy, -ilities alignment and stakeholder legibility are judgment, so they stay inside architecture-reviewer as advisory severity flags. Both halves share one lens vocabulary. Add a fourth verdict alongside pass, warn and block — disclaimer of opinion: “I could not obtain sufficient evidence to have a view.”

Basis
direct: The decision-archetypes/ precedent was measured and confirmed — 5 files, 781 lines, behind a 131-line parent. The repo already contains the tension this resolves in two places: agents/architecture-reviewer.md states “You do not gate merges,” while skills/evolutionary-architecture/SKILL.md states fitness-check “Failures gate.” The report format already has an “(If none: …)” fallback idiom used four times, which is the precedent the disclaimer verdict extends. external: IETF directorate reviews — many fixed perspectives, one structured template per perspective, a graded verdict — and Zimmermann's “How to review ADRs,” which argues for multiple review perspectives rather than one reviewer.
Rationale

This is the direct answer to the user's numbered list, and the shape matters more than the list. Lenses-as-files is the only construction that honours the “etc.” — a new lens is a new file, not an amendment to an agent or a new skill — while clearing every admission bar, because a lens file is neither skill nor command nor agent. The decidability split is the part nobody would arrive at from the list alone: treating all seven as advisory guarantees the mechanical ones decay, and treating all seven as gates means blocking a merge on a legibility opinion. The disclaimer verdict is what keeps the strategy and evidence lenses honest in a repo that has no strategy artifact yet — without it they either fabricate approval or fabricate a finding.

Downsides

Two mechanisms means two places a lens can be defined and drift. The advisory half is only as good as the model reading it, and severity inflation is a real failure mode once seven lenses report at once. Shipping the well-formedness lens before the drafting fixes in idea 3 would fail all four in-repo ADRs on day one and teach the team the reviewer is noise — the sequencing is not optional.

2

Ship fitness/adr-format — with the routing-table drift as its first assertion

Conformance and decision aging Confidence 92% Complexity Low
Description

Build the check the plugin has been citing as its canonical worked example in three separate files and has never written. Give it two first occupants that both have real, present-tense failures: that every ADR matches the template the skill teaches, and that every surface naming the routing table agrees on which file it is. It runs inside the existing node:test suite — no new dependency, no new runner, no scheduler.

Basis
direct: Confirmed absent — no fitness/, scripts/fitness/ or tests/fitness/ directory exists anywhere, while fitness/adr-format.ts is named in skills/architectural-fitness-functions/SKILL.md, agents/fitness-author.md (twice) and docs/architecture.md. Confirmed drift — commands/decide.md:19 cites only ~/.claude/CLAUDE.md and never mentions ./ARCHITECTURE.md, while agents/adr-historian.md:20-25 makes ./ARCHITECTURE.md primary with the global file as fallback. Confirmed gap — no test in test/ references docs/adr/.
Rationale

The repo already wrote down its own law for this, in its own solutions store: a repoint “is a one-time edit unless enforced; the CI-gated check is what makes ‘no stale references’ a standing invariant rather than a fact that decays.” It has never applied that law to its own routing table, and the historian is being sent to the wrong file today as a result. This is also the cheapest possible proof of idea 1's mechanical half — it establishes the check, the runner and the reporting shape before any lens work depends on them.

Downsides

A naive template assertion fails immediately, and not only on the options table: the four existing ADRs are not internally consistent with each other — 0001 has no revisit-triggers section at all, 0002 uses an H2 heading for it, and 0003 and 0004 use H3. Deciding what the check asserts means first deciding which of those is correct, which is real work disguised as a lint. Expect to ship it with a small number of assertions and grow it.

3

The evidence loop: an Evidence column where assumed is legal and printed

Drafting and evidence Confidence 80% Complexity Medium
Description

Add a sixth column to the taught options table whose legal values are spike:, benchmark:, production:, prior-adr: or assumed. The point is not to force a spike on every decision — it is to make unevidenced scoring visible on every review, exactly the way the fitness skill already handles unenforced characteristics with a declared gap. Pair it with two upstream changes: a Proposed ADR states the decisive experiment and the result that would settle it before the spike runs, and /decide pre-populates the options table from data it already computes — archetype integrator and disintegrator scores, radar rings — so the author edits a table instead of authoring one from nothing.

Basis
direct: The evidence axis is empty and this was verified twice — a repo-wide grep for spike|prototype|proof of concept|PoC|benchmark returns exactly one hit, an unrelated homonym in the characteristics skill. The five taught dimensions (Complexity, Reversibility, Team familiarity, Operational overhead, Cost) are all judgments with no provenance column. Meanwhile the options table itself appears in zero of the four real ADRs, despite skills/architectural-trade-offs/SKILL.md already instructing that its Step-3 scoring table be handed off into “Options considered.” The assumed idiom is not invented: the fitness skill already specifies a declared gap “encoded with a skip result and a reason string — promises to self, not forgetting.” external: Bezos on one-way doors — “every day you keep a one-way door open you can gather evidence” — which gives the evidentiary bar a principled trigger proportional to irreversibility.
Rationale

This is the user's criterion 6, and it is the largest documented hole in the corpus: an architecture-practice plugin with no word for a spike is a machine for producing confident, unsourced comparison tables. It is also the diagnosis that makes the options-table failure tractable — the hand-off is already instructed and still isn't landing, so the problem is not missing guidance, it is that authoring a five-dimension table from a blank template predictably gets skipped. Pre-filling converts “author this” into “edit this.” And reusing the declared-gap convention means the fix ships as an idiom the plugin already teaches rather than a new discipline to adopt.

Downsides

assumed is a permitted escape hatch, so a team can satisfy the letter of the lens while evidencing nothing; the countermeasure is counting assumed values, which is another thing to build. Pre-registration adds a step to a flow whose current problem is already that authors skip steps. Routing to a prototyping skill is a weaker fit than it first appears — ce-prototype is scoped to how something should work, feel or read, explicitly not to deciding what to build, and a decisive architecture benchmark is a different job.

4

Make decision state readable: status at session start, decisions at edit time

Decision-state awareness Confidence 84% Complexity Low
Description

Two moves on one axis. First, extend the session-start loop to read each ADR's ## Status line and report a status mix and a Proposed backlog instead of a file count. Second — the bigger one — stop treating context-loading as a push at session start and make it a lookup at edit time: a Write|Edit pre-tool check that resolves which accepted decisions govern the path being edited and injects only those. Both surfaces carry the same payload: a required one-sentence Y-statement per ADR (“In the context of X, facing Y, we decided Z, to achieve Q, accepting D”), authored once by the decision's owner instead of improvised per query.

Basis
direct: hooks/session-start.sh:40-47 was read and does exactly find … | wc -l plus find … | sort -r | head -3 | xargs basename — no file body is opened. .claude-plugin/hooks.json was verified to already register a Write|Edit PreToolUse matcher (for deps-pretooluse.sh), so the shape being reused exists and needs no new hook. The historian's report template is confirmed to be “title — one-line why relevant,” where that line is improvised per query. external: Repowise's get_why(path) for agents before editing; and the 2026 “Context Matters” finding that context selection is the accuracy bottleneck and too much context degrades output — which makes path-keying an accuracy argument, not just a size one.
Rationale

The hook's own comment claims it replaces the manual “did I check the ADRs?” discipline, and it replaces only the counting half. The status read is a few lines of bash against a heading every ADR already has. The path-keyed lookup is the more consequential half and needs a governs pointer per ADR — which, kept as a flat comma-list, stays inside what the repo's existing frontmatter parser can read, unlike the richer decision-graph proposals that were cut for exactly this reason.

Downsides

A governs list is hand-maintained and will rot; a wrong path mapping is worse than none because it injects a confident irrelevance. Firing on every Write|Edit competes for attention with the dependency hook already on that matcher, and ADR-0002 names hook noise as a live negative with its own revisit trigger at more than two hooks disabled. The Y-statement is a required field that only helps if authors write it well.

5

Drivers as a numbered ADR — a utility tree the lenses can check against

Decision drivers Confidence 75% Complexity Medium
Description

The instinctive move is a new STRATEGY.md or drivers file. Do the opposite: ship the drivers as a numbered ADR, shaped as an ATAM-style utility tree — business goal, then quality-attribute scenarios, then prioritized characteristics each carrying its measurement. Every later ADR then cites a specific leaf. That gives lenses 3 and 4 something concrete to check alignment against, instead of an opinion about a document nobody wrote.

Basis
direct: skills/architectural-characteristics/SKILL.md already does business-goal-to-characteristic translation, forces a top-3-firm-plus-4-soft cut, states that the prioritization “IS an architectural decision; treat it like one,” and adds “measurement = no fitness function = not chosen.” Verification confirmed there is no characteristics-prioritization ADR among 0001–0004, and zero cross-link from commands/decide.md back to the characteristics skill. The plugin's own dogfooded docs/architecture.md carries a real Firm/Soft characteristics table — proving the gap is felt — with no ADR behind it. A filesystem search for strategy, product, drivers, requirements, constraints, principles, roadmap or charter files returns only that one file. external: ATAM utility tree (business drivers → quality-attribute scenarios → prioritized leaves); arc42 §10 and ISO 25010 for the quality vocabulary, used as a quality model rather than a record format — the 2026 template study ranked arc42 worst as an ADR template.
Rationale

This is the thinnest stage in the lifecycle and the second thing the user named. Inventing a new artifact type would also collide with the plugin's own stated anti-pattern about dumping decisions into the routing table. The Firm/Soft grading already exists as vocabulary and is completely inert — nothing consumes it. Making it the alignment target turns “alignment with the -ilities” from a subjective checkbox into a graded standard, and lets a Firm characteristic raise the evidentiary bar in idea 3 while a Soft one does not.

Downsides

It only works if aligns_with stays free text — a typed field runs into the same parser ceiling that cut the decision-graph ideas. A drivers ADR is also a decision that will itself need superseding, and prioritized characteristics are exactly the thing teams argue about longest, so the first one is expensive to land. And it cannot fix the product-strategy lens by itself: the plugin has no authority over a product's strategy document and must only point at one, per the cross-product scope line.

6

Right-size the ceremony: triage first, then tier by level × reversibility

Decision drivers Confidence 68% Complexity Medium
Description

Every other idea here raises the cost of an ADR, so add the control that makes them affordable. Put significance triage at step zero of /decide — the skill's own three triggers, which nothing currently runs — with a lightweight log for the decisions it turns away, so they are recorded rather than dropped. Then replace the binary “one-way doors get an ADR” rule with a tier computed from two values the plugin already has: the decision's governance level and its Reversibility score. The tier picks the template weight and which of idea 1's lenses apply.

Basis
direct: The binary is explicit — “Write an ADR for one-way doors” and “Skip the ADR for two-way doors.” Both inputs are confirmed present and independent: Reversibility is one of the five core options dimensions, and skills/architecture-governance-levels/SKILL.md states the level determines “which repo's docs/adr/ is the right home … who has authority … how the decision propagates downward,” with “Higher levels constrain lower levels.” The three ADR-worthiness triggers are confirmed in the skill and confirmed to be run by nothing — commands/decide.md step 1 presupposes the ADR. external: the recurring RFC pattern of tiered templates — lightweight for team scope, heavyweight for org-wide — at Squarespace, Uber and Google.
Rationale

At scale the dominant failure of ADR programs is over-recording, not under-recording, and a seven-lens reviewer set applied uniformly is unusable at service level and under-specified at enterprise level. The plugin already computes both inputs and discards the combination. Triage is the other half: without a gate, improving the lifecycle makes the volume problem worse, and the rubric for it is already written — orphaned behind a reference to a skill this repo does not contain.

Downsides

Tiering is a policy, and the tier boundaries will be argued about more than they are used; a wrong tier silently skips the lens that would have caught the problem. Reversibility is self-scored by the author, so it is gameable in the direction of less work. And a triage gate that turns decisions away needs its log to be genuinely cheap, or it just becomes a second place where decisions go to be forgotten.

7

Decision aging without a scheduler

Conformance and decision aging Confidence 72% Complexity Medium
Description

Give the retirement stage — currently the one stage with literally zero mechanism — three inputs feeding one state. A revisit trigger written as a checkable predicate where one exists. A deterministic staleness signal: the paths a decision governs have newer commits than the decision itself, with no model in the loop. And a structured observed-outcome note appended to a live ADR — what we predicted, what actually happened, dated — so operating experience amends the decision by default instead of requiring a full supersession. Any of the three moves the ADR to Revisit-due, which the session-start briefing surfaces until someone re-affirms it with a dated line or supersedes it. It rides the existing PR-triggered test run, because this repo has no cron.

Basis
direct: The skill's own wording is already a covenant definition — revisit triggers are “specific, measurable conditions … not ‘we might reconsider someday’ but ‘if X exceeds Y, evaluate alternative Z.’” The ADRs write them that way, and nothing reads them: the one firing on record was noticed by a human and narrated as prose inside a successor document. The repo also contains a textbook adverse event discovered years late — ADR-0004 records that ADR-0002's mechanism “never worked … absent at HEAD and absent at every revision in history. The decision was recorded but never realized” — plus a live, self-reported, unrouted one: “Nothing enforces the match.” The expiry pattern already exists for a different object: “every flag has an expiration date — flags older than N months fail fitness.” external: Repowise's deterministic staleness rule, and post-market surveillance, where a drug's label accumulates real-world evidence without the drug being withdrawn.
Rationale

“Recorded but never realized” is a failure neither existing mechanism catches: conformance review compares the diff to the ADR, so it never fires for a decision that produced no diff at all, and supersession requires someone to already know the decision is wrong. The deterministic staleness signal is the one input here that costs nothing and cannot hallucinate. And the plugin telling its users to expire their feature flags while having never expired a decision is the whole argument for this stage in one line.

Downsides

Verification found no schedule: or cron: anywhere in the five workflows, so the “periodic” framing had to be dropped — aging only gets evaluated when someone opens a PR, which means a quiescent repo ages silently. Only a subset of triggers are ever going to be machine-checkable (“a second consumer plugin repoints” is not), and it must be explicit that the unstructured ones stay unevaluated rather than implying coverage that does not exist. A Revisit-due state that nobody clears becomes background noise within a quarter.
